-----------------------------------------------------------------------
1. OBIETTIVO
-----------------------------------------------------------------------
Un'integrazione per Home Assistant ("Climaoro") che gestisce in modo
centralizzato i termostati autonomi (Climaoro): l'utente la installa,
inserisce le entità corrette (con i selettori, come nelle automazioni),
e a quel punto l'integrazione crea TUTTO in automatico: entità di
contorno, config AppDaemon, pannello di controllo.

Il motore logico resta AppDaemon (disabilita la funzione autonoma dei
termostati e li pilota collettivamente: gruppi, 2 fasce eco/comfort,
delta per gruppo, calendario 7x24 per gruppo, soglia pesi, priorità,
emergenza individuale).

-----------------------------------------------------------------------
2. ARCHITETTURA ATTUALE (funzionante e testata end-to-end)
-----------------------------------------------------------------------
- Custom component in /config/custom_components/climaoro/ con Config
  Flow (wizard con selettori entity). NIENTE entity_id hardcoded.
- L'integrazione crea in HA le entità di contorno:
  * switch.climaoro_attivo (master)
  * number.climaoro_soglia_pesi
  * number.climaoro_<gruppo>_delta_comfort / _delta_eco (per gruppo)
  * number.climaoro_<stanza>_peso
  * switch.climaoro_<stanza>_inclusione
  * sensor.climaoro_<gruppo>_calendario
  Tutte scrivono le modifiche nelle OPTIONS della config entry
  (verificato: change del number delta -> propagata a /api/climaoro/config).
- L'integrazione espone la CONFIG RUNTIME GENERICA:
  * REST  /api/climaoro/config
  * WS    climaoro/config
  Struttura: { global, gruppi[], entities{} } con gli ENTITY_ID CORRENTI
  risolti dal registry HA (unique_id -> entity_id). Se l'utente rinomina
  un'entità, app e pannello continuano a funzionare (rename-proof).
  Per le 4 entità chiave della stanza (clima, temp_salvata, modalita,
  rinnovo) il wizard salva ANCHE l'unique_id -> risoluzione rename-proof.
- App AppDaemon GENERICA (appdaemon/climaoro.py): unica classe, args
  ha_url + ha_token (+ refresh_sec/cycle_sec/rinnovo_sec). Non conosce
  alcuna entità: legge /api/climaoro/config a ogni refresh e usa gli
  entity_id risolti. Logica: fascia oraria -> delta gruppo; zone in
  riscaldamento = priorità; altrimenti soglia pesi (accensione
  collettiva); altrimenti emergenza individuale (temp <= guardia - 0.4).
  Sicurezza: prima di un comando a un climate accende automaticamente
  lo switch modalita_centralizzata se spento.
- Pannello frontend: dashboard LOVELACE storage "Climaoro"
  (url_path climaoro-panel) creata via websocket dal file locale
  .storage/lovelace.climaoro_panel, costruita dagli entity_id risolti
  (non hardcoded). Card: globale + per gruppo (delta, calendario) +
  per stanza (climate, temp_salvata, peso, inclusione, modalita, rinnovo).
- Simulazione senza dispositivi reali: entità finte in configuration.yaml
  (sim_input_number.yaml, sim_input_boolean.yaml, sim_input_button.yaml,
  sim_template.yaml, sim_climate.yaml - vedi sotto).
